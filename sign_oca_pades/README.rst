This module seals the documents signed with ``sign_oca`` with PAdES
signatures, so that any later change to a signed document can be
detected with a standard PDF reader.

- Before its first seal, the document becomes a PDF form: one read-only
  field per item (a check box for a check item, a multi-line text field
  for the others), one signature field per signer over the box of its
  signature item, and pages reserved at the end for the signature
  certificate (two by default). This happens when the request is sent,
  or at the first signature for a request sent before a certificate was
  configured.
- Each signature is written as an incremental update of the PDF that
  fills the fields of the signer (each one shows the item as
  ``sign_oca`` draws it) and is sealed at once with a PAdES baseline
  signature (``ETSI.CAdES.detached``, SHA-256) in the signer's signature
  field, which shows the signature image. Earlier seals stay valid: the
  bytes they cover are never rewritten, and the later updates only fill
  form fields, which PDF readers and pyHanko's difference analysis
  accept after an approval signature.
- Each signer's signature field locks the fields of the signer's role
  (FieldMDP) and allows later revisions to fill the form and sign only:
  a verifier reports a value or an appearance rewritten after the seal.
  A stamp of a signer without signature image, such as a refusal or a
  tier approved by bypass, still seals the signer's own field with a
  blank appearance, so that no empty signature field is left for a later
  signature. The field keeps the name it was prepared with, whatever
  happens to its role afterwards.
- When the last signer signs, or when the process ends on a refusal (see
  ``sign_oca_tier_validation``), the signature certificate fills the
  reserved pages, and the whole document gets a final seal, which locks
  every field and allows no later change. A certificate longer than the
  reserved pages is rendered again at a smaller zoom, down to 60 %, so
  that its text reflows to the page width. The certificate lists the
  signers in signing order, each signature or refusal with the channel
  it was made from (portal, back office or server), the hash chain
  status, and the activity log with channel, IP address and user agent.
  Every time is printed in UTC, followed by the local time in
  parentheses. A signer approved without a signature of their own (a
  tier approved by bypass in ``sign_oca_tier_validation``) is listed as
  such, not as pending.
- The reason of a seal names the signer (``_pades_seal_signer_name`` of
  the signer) and their role; a module stamping a decision that is not a
  signature gives its own reason in the context key
  ``sign_oca_stamp_reason``.
- With a timestamp authority (RFC 3161), every seal carries a trusted
  timestamp. When the authority does not answer, the seal is applied
  without timestamp and a message is posted on the request.
- The request keeps the SHA-256 of the original and of the final
  document, the SHA-256 of the certificates that sealed it, and a
  summary of its seals (number, all intact or not, last check) that the
  "Verify Seals" button refreshes. A seal made by another certificate,
  or a document that differs from the final one, is reported.

Without sealing certificate the signatures are not sealed: documents are
produced as ``sign_oca`` makes them, a warning is logged, and the
request shows that the document is not sealed. The certificate page is
still appended when the last signer signs, as an unsealed incremental
update. A document already prepared as a form keeps being filled field
by field, unsealed.

Configuration
=============

The seal needs a PKCS#12 file (``.p12`` or ``.pfx``) holding a private
key and its certificate. It is read from the first source that provides
one:

1. The server configuration file (``odoo.conf``, section ``[options]``):

   .. code:: ini

      sign_oca_pades_pkcs12_path = /path/to/seal.p12
      sign_oca_pades_pkcs12_password = secret
      sign_oca_pades_tsa_url = https://tsa.example.com

   The file stays on the server and never enters the database.

2. The company: go to *Sign > Settings > General settings*, section
   *Document Sealing (PAdES)* (visible to administrators only), and
   upload the PKCS#12 file with its password. An optional *Timestamp
   Authority* URL can be set there too.

A timestamp authority URL from the configuration file takes precedence
over the one of the company.

The module depends on the Python library ``pyhanko``. Install
``pyhanko<0.26``: pyHanko 0.26 and later require ``lxml>=5.4``, while
Odoo 18 environments commonly pin an older ``lxml``. Version 0.25.3 is
the one this module is tested with.

The local times of the certificate page use the time zone of the
request's tier validation when ``sign_oca_tier_validation`` sets one,
else the time zone of the company's contact, else UTC.

Usage
=====

1. Configure a sealing certificate (see *Configuration*).
2. Send a sign request as usual. The document receives its form fields
   and the pages reserved for the certificate. Each time a signer signs,
   the signer's fields are filled and a new seal signs the signer's
   signature field.
3. When the last signer signs, the certificate fills the reserved pages
   and the final seal is added. The signed copy mailed to the signers is
   the sealed one.
4. On the request, the *Seals* section shows the seal status, the number
   of seals, the original and final SHA-256 and the result of each seal
   check. *Verify Seals* checks the stored document again.

The seals can also be checked in any PDF reader that supports
signatures: each one is shown as valid as long as the bytes it covers
are unchanged. Whether the certificate is trusted depends on the reader
and on the certificate authority that issued it.

Known issues / Roadmap
======================

- Embed revocation information (PAdES B-LT) and a document timestamp
  (PAdES B-LTA) for long-term validation.
- Allow ``pyhanko>=0.26`` once ``lxml>=5.4`` can be installed alongside
  Odoo.
- Certificate pages are drawn as page images: their links and
  annotations are not kept.
- Two pages are reserved for the certificate, and the page count of a
  sealed document cannot change: a longer certificate is first rendered
  at a smaller zoom, then, when even 60 % does not fit, its last pages
  are printed smaller, laid out in a grid on the last reserved page. A
  module can reserve more pages by overriding
  ``_pades_certificate_page_count``.
- pyHanko applies a field lock to every field whose name starts with a
  locked name and treats an appearance stream written before a seal as
  rewritten by every later revision; the item fields are therefore named
  with a fixed number of digits, and a seal writes again the appearance
  streams of the fields it locks.
- A refusal outside a tier validation does not finalize the document:
  ``sign_oca_refuse`` has no hook that runs after every module's
  ``_on_refuse``, where ``_pades_finalize`` would be called.
